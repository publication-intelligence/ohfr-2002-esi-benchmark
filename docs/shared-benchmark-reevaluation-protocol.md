# Four-index reevaluation protocol

The user authorized migration and reevaluation of Published, IndexPDF, IndexerLabs and Indexia against the independently reviewed successor, with commits and relevant PR merges. Execution begins after the actual source freeze, shared policy and density lock, and verified methodology installation are available. This protocol records the study's review procedure; it changes no V8.2 formula, weight, judgment meaning or denominator.

## Inputs and preservation

Each owner receives the same exact source release, original draft and independent review, source-only frozen state, page map, 17-chunk manifest, shared policy template, density evidence and study lock. The methodology installation and each candidate's previous canonical state are bound by exact hashes. The approval records the user's existing instruction and actual candidate visibility. It does not claim new candidate-blind discovery.

Preserve each historical state, original policy and benchmark, complete private checkpoint, normalization evidence and correction/adjudication ledgers. Existing source-region and registration warnings remain historical evidence. Any necessary current source-inventory repair receives a new artifact and truthful registration; it must not silently alter a preserved freeze.

Use the typed retrospective migration command. Its `audit_transfer_authorized: false` boundary remains intact. Candidate normalization can remain if exact delivered-file, normalized-content and page-map identities and prior fidelity corrections are verified. The migration does not itself approve any old audit judgment.

## Delivered-locator and physical-reference evidence

The four private triage inventories enumerate existing evidence and review flags. A missing dependency keyword does not prove independence from the old benchmark. A missing separate rationale field or null normalized reference target does not by itself prove an index defect.

For every reused judgment, establish that the same delivered candidate path/reference and source page are under review; the exact frozen source eligibility and judgment rules apply; and its evidence and rationale answer the complete current requirement. Review flagged ambiguities, adverse or partial findings, policy-region questions and previous corrections explicitly. Retain an exact-ID compatibility disposition and artifact bindings. Reuse the existing evidence transparently where justified, distinguishing its original inspection from the current compatibility review. Otherwise conduct a fresh review. No bulk replacement of benchmark hashes, subject IDs or judgment labels establishes compatibility.

Physical reference destinations and typography remain candidate facts. Required reference obligations, their relevance and consequences must be reconsidered under the new benchmark and policy. Preserve uncertainty rather than manufacturing a destination or treating a normalization limitation as total wrongness.

## New benchmark-dependent audits

Rebuild ownership and worksets against the actual frozen successor. Every worker must receive the complete frozen parent subject/task records, evidence, required access facets, scope rules and retained source distinctions, together with all referenced subjects across chapter boundaries. Workset IDs and locator packets alone are insufficient.

Reassess every current subject, treatment, reader task and relevant relationship/access obligation. Historical missing-access ledgers are evidence to consult, not judgments to relabel. Reevaluate structure's semantic claims, warranted references, applicability and implied passes, preserving direct physical evidence where justified. Rebuild density from the exact shared ordered chunk measurements and reconsider all uncertainty scopes. Old totals, omission lists, fixed gate prose and candidate-specific score constants are not inputs to new judgments.

Consolidated requirements retain one parent scoring unit. Their facets are unweighted detail that auditors must consider before assigning the existing parent judgment. A broadly related heading does not demonstrate success on every specific question. Parent task bindings must carry all required subject bindings; partial or unresolved access remains explicit under the established rubric.

Each owner supplies a separate private factual review receipt bound to the final benchmark, candidate and audit bytes. It enumerates `(parent kind, parent ID, facet ID)` and the reviewed scope rules and retained distinctions, with concrete tested candidate paths, evidence references, dispositions and the resulting parent judgment. It must be written from actual review. An expected-ID list, schema pass or copied completion flag is not a review. Unresolved items must be identified honestly. This receipt is study QA evidence; it adds no scored units, deterministic facet aggregation or new generic audit-schema requirement.

## Results and integration handoff

After the audits are complete, run the supported registrations, scoring, report generation and checkpoint validation with the installed reviewed methodology. Preserve observed and adjusted views and the actual correction provenance; do not assume score invariance after a substantive benchmark change.

Each owner returns a complete private checkpoint, exact current-state/report/projection identities, validation results and a concise explanation of changed findings. The coordinator verifies shared preflight across all four states and assembles one public comparison bundle with the exact registered report and collection bytes. No mixed benchmark, policy, source scope, calculation profile or density basis may enter the comparison.

The website importer consumes that verified bundle atomically. Review benchmark/methodology identity, all four result views, gates, detailed source requirements and lazy evidence links using the actual new data. Public requirements use the producer's explicit safe projection; private authored stance and other restricted rationale remain private. Complete local/browser checks and PR validation before the integration merge. Deployment remains a separate action and has not been authorized.
